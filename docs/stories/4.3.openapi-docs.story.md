## Story

**As a** e-commerce developer (or future integration partner),
**I want** a machine-readable OpenAPI 3.1 specification for the `/api/v1/` bridge,
**so that** I can understand available endpoints, required headers, request/response schemas, and error codes without reading the source code (spec.md FR-12, CON-2, Epic 4 checklist — "Documentação OpenAPI para app/api/v1/").

## Acceptance Criteria

1. **OpenAPI spec file** — `public/openapi.yaml` is created with a valid OpenAPI 3.1.0 document:
   - `info.title`: `"Gestão Loja de Óculos — E-commerce Bridge API"`
   - `info.version`: `"1.0.0"`
   - `servers`: `[{ url: "/api/v1", description: "E-commerce Bridge" }]`
   - `components.securitySchemes.ApiKeyAuth`: `{ type: apiKey, in: header, name: X-Api-Key }`
   - `security`: `[{ ApiKeyAuth: [] }]` applied globally (all routes require the key)
   - (FR-12, CON-2, CON-5)

2. **`GET /products` endpoint** — documented in `public/openapi.yaml`:
   - Query parameters: `format` (string, enum `[json, csv]`, default `json`), `supplierId` (string, optional), `brand` (string, optional), `includeArchived` (boolean string `"true"`, optional)
   - Response `200` for `format=json`: `application/json` — array of `ExportProduct` (see schema below)
   - Response `200` for `format=csv`: `text/csv` — raw CSV string
   - Response `401`: `{"error": "Missing or invalid API key"}`
   - Response `500`: `{"error": "Failed to export catalog"}`
   - (FR-12, CON-2)

3. **`GET /inventory` endpoint** — documented in `public/openapi.yaml`:
   - No query parameters
   - Response `200`: `application/json` — array of `InventoryEntry`:
     `{ variantId: string; sku: string; productName: string; quantity: integer; minStockAlert: integer; isLowStock: boolean }`
   - Response `401`: standard error object
   - Response `500`: `{"error": "Failed to fetch inventory"}`
   - (CON-2)

4. **`GET /customers` endpoint** — documented in `public/openapi.yaml`:
   - No query parameters
   - Response `200`: `application/json` — array of `Customer`:
     `{ id: string; name: string; phone: string|null; email: string|null; tags: string[]; createdAt: string (ISO 8601) }`
   - Response `401`: standard error object
   - Response `500`: `{"error": "Failed to fetch customers"}`
   - (CON-2)

5. **`POST /customers` endpoint** — documented in `public/openapi.yaml`:
   - Request body: `application/json` — `{ name: string (required); phone?: string; email?: string; tags?: string[] }`
   - Response `201`: `application/json` — `Customer` object (same shape as GET /customers item)
   - Response `400`: `{"error": "name is required"}` or `{"error": "Invalid JSON body"}`
   - Response `401`: standard error object
   - Response `500`: `{"error": "Failed to create customer"}`
   - (CON-2)

6. **Reusable schemas** — `public/openapi.yaml` `components.schemas` defines:
   - `ExportVariant`: `{ id, sku, frameColor, lensColor, uvProtection, isPolarized (boolean), price (string — decimal), stock (integer), images (string[]) }`
   - `ExportProduct`: `{ id, name, brand, description (string|null), supplierId (string|null), variants (ExportVariant[]) }`
   - `InventoryEntry`: fields from AC-3
   - `Customer`: fields from AC-4
   - `ErrorResponse`: `{ error: string }`
   - (FR-12, CON-2)

7. **`GET /api/v1/openapi` route** — `src/app/api/v1/openapi/route.ts` (no auth required — spec is not sensitive):
   - Reads `public/openapi.yaml` from the filesystem using `node:fs/promises`
   - Parses YAML using `js-yaml` (already a transitive dependency via dev tooling; confirm availability or import from `yaml` package if needed)
   - Returns the parsed object as `application/json` with `Cache-Control: public, max-age=3600`
   - This route must be excluded from the middleware matcher — the `config.matcher` in `src/middleware.ts` already matches `/api/v1/:path*`; add explicit exclusion: `'/api/v1/openapi'` is NOT protected (return `NextResponse.next()` before key check when `request.nextUrl.pathname === '/api/v1/openapi'`), OR change the matcher to `/api/v1/(products|inventory|customers)/:path*` to exclude openapi by design
   - (CON-2, CON-5)

8. **Middleware exclusion** — `src/middleware.ts` is updated so that `GET /api/v1/openapi` is publicly accessible without an API key:
   - Approach: add a pathname check before the key validation:
     `if (request.nextUrl.pathname === '/api/v1/openapi') return NextResponse.next()`
   - Existing backoffice routes and all other `/api/v1/` routes remain protected
   - (CON-5)

9. **Typecheck + lint** — `npx tsc --noEmit` and `npm run lint` pass with zero errors; no new test file required (the route is a thin adapter; the YAML file is static and validated by its schema structure).
   - (CON-2)

### YAML Dependency for the Route

Check if `js-yaml` or `yaml` is available as a project dependency:
- Run `cat package.json | grep -E '"js-yaml|"yaml'` — if neither is present, use `yaml` (pure ESM, commonly available) or add `js-yaml` with `npm install js-yaml` + `npm install -D @types/js-yaml`
- Alternative (no new dep): parse the YAML manually by reading the file and returning it as-is with `Content-Type: application/yaml`, OR maintain a parallel `public/openapi.json` static file and serve it directly via `readFile`
- Simplest zero-dependency approach: keep `public/openapi.yaml` as the human-readable source AND add `public/openapi.json` as the machine-readable copy; the route at `/api/v1/openapi` serves the JSON directly without parsing

### Technical Constraints
- **No `'use client'`**: route handlers are pure server-side — no directive needed
- **Middleware exclusion**: pathname-based bypass is the minimal-change approach; do NOT change the matcher regex as it would require careful escaping
- **Static YAML only**: no code-generation from TypeScript types (that would require additional tooling out of scope)
- **`public/` is served by Next.js**: `public/openapi.yaml` is accessible at `/openapi.yaml` after deployment — the route at `/api/v1/openapi` adds a stable JSON-serving endpoint for API clients
