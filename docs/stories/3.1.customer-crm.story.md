## Story

**As a** store owner,
**I want** to register customers with their contact information and preference tags, view their purchase history, and optionally link a sale to a registered customer at the PDV,
**so that** I can identify recurring customers, understand their buying preferences, and increase retention and average ticket (spec.md Section 3.4, FR-6, AC-6.1 – AC-6.4).

## Acceptance Criteria

1. `src/features/customers/customer.contract.ts` — exports public types:
   - `CustomerRecord`: `{ id: string; name: string; phone: string | null; email: string | null; tags: string[]; createdAt: Date; updatedAt: Date }`
   - `CustomerSummary`: `{ id: string; name: string; phone: string | null; email: string | null; tags: string[]; saleCount: number; createdAt: Date }`
   - `CreateCustomerDTO`: `{ name: string; phone?: string; email?: string; tags?: string[] }`
   - `UpdateCustomerDTO`: `{ name?: string; phone?: string; email?: string; tags?: string[] }`
   - All types barrel-exported from `src/features/customers/index.ts`
   - (FR-6)

2. `src/features/customers/services/customer.service.ts` — `CustomerService` class:
   - `getCustomers(search?: string): Promise<CustomerSummary[]>` — returns all customers with sale count; optionally filters by name/phone/email (case-insensitive `contains`); ordered by `name ASC`
   - `getCustomerById(id: string): Promise<CustomerWithSales>` — returns customer with full sale history (items count, amount, date); throws `Error('Cliente não encontrado')` if not found
   - `createCustomer(dto: CreateCustomerDTO): Promise<CustomerRecord>` — validates `dto.name` non-empty (throws `Error('Nome obrigatório')`); creates customer; `tags` defaults to `[]`
   - `updateCustomer(id: string, dto: UpdateCustomerDTO): Promise<CustomerRecord>` — validates customer exists before update (throws `Error('Cliente não encontrado')`); patches only provided fields
   - `searchCustomers(q: string): Promise<{ id: string; name: string; phone: string | null }[]>` — lightweight search for PDV autocomplete (name/phone contains query, limit 10, ordered by name)
   - (FR-6 AC-6.1, AC-6.2, AC-6.3, AC-6.4)

3. `src/features/customers/actions.ts` — Server Actions (`'use server'`):
   - `getCustomersAction(search?)` — calls `CustomerService.getCustomers(search)`, maps to serializable DTO (`createdAt` as ISO string)
   - `getCustomerByIdAction(id)` — calls `CustomerService.getCustomerById(id)`, maps sale dates to ISO strings
   - `createCustomerAction(dto)` — calls `CustomerService.createCustomer(dto)`; on success `revalidatePath('/clientes')`; returns `{ success: true; id: string }` or `{ success: false; error: string }` (never throws)
   - `updateCustomerAction(id, dto)` — calls `CustomerService.updateCustomer(id, dto)`; on success `revalidatePath('/clientes')`; returns `{ success: true }` or `{ success: false; error: string }`
   - `searchCustomersAction(q)` — calls `CustomerService.searchCustomers(q)`; returns `{ success: true; customers: [...] }` or `{ success: false; error: string }`
   - (FR-6)

4. `app/(backoffice)/clientes/page.tsx` — Server Component (replaces placeholder):

### Prisma Schema — Customer (DM-6) and Sale (DM-7) Relation
[Source: prisma/schema.prisma:87-112]

```prisma
model Customer {
  id        String   @id @default(cuid())
  name      String
  phone     String?
  email     String?
  tags      String[]
  sales     Sale[]
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt
}

model Sale {
  id               String         @id @default(cuid())
  totalAmount      Decimal        @db.Decimal(10, 2)
  paymentBreakdown Json
  status           SaleStatus     @default(COMPLETED)
  refNfe           String?
  customerId       String?
  customer         Customer?      @relation(fields: [customerId], references: [id])
  items            SaleItem[]
  cashFlowEntry    CashFlowEntry?
  createdAt        DateTime       @default(now())
  updatedAt        DateTime       @updatedAt
}
```

**Key points:**
- `Customer.tags` is `String[]` — already JSON-safe, no special serialization needed
- `Sale.customerId` is `String?` — relation is optional; sales without a customer are the default flow
- No schema migration needed — both `Customer` and `Sale.customerId` already exist in the schema

### CustomerService — Pattern Reference
[Source: src/features/cashflow/services/cashflow.service.ts — static class pattern]

```typescript
// src/features/customers/services/customer.service.ts
import { prisma } from '@/lib/prisma'
import type { CustomerRecord, CustomerSummary, CreateCustomerDTO, UpdateCustomerDTO } from '../customer.contract'

export class CustomerService {
  static async getCustomers(search?: string): Promise<CustomerSummary[]> {
    const customers = await prisma.customer.findMany({
      where: search
        ? {
            OR: [
              { name: { contains: search, mode: 'insensitive' } },
              { phone: { contains: search, mode: 'insensitive' } },
              { email: { contains: search, mode: 'insensitive' } },
            ],
          }
        : undefined,
      include: {
        _count: { select: { sales: true } },
      },
      orderBy: { name: 'asc' },
    })

    return customers.map((c) => ({
      id: c.id,
      name: c.name,
      phone: c.phone,
      email: c.email,
      tags: c.tags,
      saleCount: c._count.sales,
      createdAt: c.createdAt,
    }))
  }

  static async createCustomer(dto: CreateCustomerDTO): Promise<CustomerRecord> {
    if (!dto.name?.trim()) throw new Error('Nome obrigatório')

    return prisma.customer.create({
      data: {
        name: dto.name.trim(),
        phone: dto.phone?.trim() || null,
        email: dto.email?.trim() || null,
        tags: dto.tags ?? [],
      },
    })
  }
}
```

**CRITICAL:** `getCustomers` uses `include: { _count: { select: { sales: true } } }` — this avoids N+1 queries. Never count sales in application code via a separate query loop.

### PDV Customer Search Combobox
[Source: FR-6 AC-6.4 — "Venda pode ser vinculada a cliente cadastrado (opcional)"]

The combobox is positioned in the cart right panel, above the payment section. Implementation pattern:

```typescript
// State additions to PdvClient
const [customerQuery, setCustomerQuery] = useState('')
const [customerResults, setCustomerResults] = useState<{ id: string; name: string; phone: string | null }[]>([])
const [selectedCustomer, setSelectedCustomer] = useState<{ id: string; name: string } | null>(null)
const [isSearching, startSearchTransition] = useTransition()

function handleCustomerSearch(q: string) {
  setCustomerQuery(q)
  if (q.length < 2) { setCustomerResults([]); return }
  startSearchTransition(async () => {
    const result = await searchCustomersAction(q)
    if (result.success) setCustomerResults(result.customers)
  })
}

// On confirm:
await createSaleAction({
  items: ...,
  paymentBreakdown: ...,
  customerId: selectedCustomer?.id,
})

// Clear on success or clearCart:
setSelectedCustomer(null)
setCustomerQuery('')
setCustomerResults([])
```

**Min 2 chars before searching** — prevents unbounded queries on the customer table.

**CRITICAL — Two independent `useTransition` hooks:** The PDV client already uses `const [isPending, startTransition] = useTransition()` for the sale confirm action. Customer search requires a **separate, independent** transition:
```typescript
const [isSearching, startSearchTransition] = useTransition()
```
Do NOT reuse the sale `startTransition` for customer search — they serve different pending states and must not interfere. The sale `isPending` gates the Confirm button; `isSearching` gates the search dropdown only.
